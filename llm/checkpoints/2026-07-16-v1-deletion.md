## Product decisions carried forward

- Wharfie carries a useful local program beyond a coding/chat session: a normal
  TypeScript CLI can become one portable executable, a durable resident service,
  and eventually a service placed across trusted machines without an
  application rewrite.
- Nodes are trusted. A trustless or Byzantine mesh is out of scope.
- TypeScript/Node is the only initial authoring and orchestration model. The
  activity boundary must leave room for target-specific Node-API modules and
  later WASI/WASM or persistent subprocess workers; Wharfie is not a general
  multi-language build system.
- Wharfie is not general cloud IaC. A packaged application may use a user's
  normal provider credential chain to plan and create only the finite resources
  required by Wharfie capabilities.
- One coordinator is sufficient initially, provided its authority is fenced at
  a linearizable durable-store boundary and another process can reconstruct and
  safely assume coordination after failure.
- Physical work is at-least-once. Wharfie may claim exactly-once only for a
  managed effect whose destination atomically commits the stable effect identity
  with the business mutation. Interrupted unsafe effects become durable
  `uncertain` work instead of being silently retried.
- The web UI is secondary. The developer CLI and the reserved packaged operator
  namespace are the first control surface.
- There are no downstream users to protect. Prefer deletion and a coherent
  eventual model over compatibility layers.

## Known hard edges after deletion

These are current v2 problems, not reasons to restore v1:

1. Operation and action IDs are interpolated into `#`-delimited storage keys
   without reserving or escaping `#`. Blind `putOperation` upserts can also leave
   stale action records when an operation ID is reused with a changed graph.
   The strict manifest/identifier schema must define an unambiguous grammar, and
   persistence must define create-versus-replace semantics.
2. `ops cancel` hard-deletes operation records. An in-flight runner can write an
   action back after deletion, creating an orphan. Durable cancellation needs a
   fenced `CANCELLED` transition/tombstone and command-level success coverage
   before resident or cloud workers rely on it.
3. `load-app.js` remains a permissive compatibility compiler. It can silently
   default or drop malformed public fields. Replace it with one explicit,
   fail-fast, versioned v2 application schema.
4. The embedded public operator surface exposes only `wharfie manifest`.
   Systemd/infrastructure implementation material remains internal and must not
   be advertised as a supported command until the resident-service contract is
   deliberately wired and proven.
5. Production dependency audit policy is still open, and `@jest/globals` 30 is
   not aligned with the Jest 29 runner/types. A real moved-SEA Node-API addon
   proof also remains outstanding.
