# Explicit coordinator epoch authority checkpoint

- **Date:** 2026-07-28
- **Status:** **KERNEL IMPLEMENTED AND VALIDATED; RUNTIME ADOPTION PENDING**
- **Branch:** `agent/strict-manifest`
- **Parent before this slice:** `3c53532` (`docs: close steady-file systemd walkthrough`)

## Restart summary

The first bounded Outcome 2 kernel slice establishes one durable coordinator
authority per application. Its stable active-authority tuple is co-located with
the execution ledger, and a bound ledger atomically fences its mutations with
that tuple. A stale process may continue running, but after a successor commits
a higher epoch its old authority token cannot commit through that bound ledger.

This slice deliberately stops short of automatic failover. Initial acquisition,
current-owner heartbeat, graceful release, and caller-confirmed takeover are
explicit conditional transitions. The production operator path that owns and
audits that confirmation remains future work. A heartbeat is diagnostic evidence only.
Wharfie does not infer expiry from its age, process reachability, message
silence, or `Date.now()`.

[ADR 0033](../../docs/architecture/decisions/0033-explicit-coordinator-epoch-authority.md)
records the decision. It narrows the safe implementation order without
replacing [ADR 0002](../../docs/architecture/decisions/0002-one-recoverable-active-coordinator.md),
whose automatic-recovery outcome remains active.

## Contract implemented by the kernel

- There is at most one active coordinator authority at the durable-store
  boundary for an application.
- Authority records occupy a typed namespace in the same physical table as the
  execution ledger so one database transaction can validate authority and
  commit the ledger mutation.
- Initial acquisition conditionally creates an absent authority record.
- Heartbeat and graceful release compare the exact full active-authority
  snapshot, including record version and diagnostic metadata.
- Deliberate takeover requires explicit confirmation, compares the exact
  observed predecessor snapshot, and increments the epoch by one. Concurrent
  successors racing from the same observation cannot both win.
- Each acquisition or takeover request identity is the new session nonce. It
  must be freshly generated by production assembly and reused only for exact
  retry; sharing it between processes shares the authority token.
- Stable request receipts and strong successor readback resolve ambiguous
  conditional-write results; transport failure is not proof of transaction
  failure.
- Bound ledger mutations carry an exact condition on the stable
  active-authority tuple: schema, kind, application, coordinator, authority ID,
  epoch, and active status.
- Heartbeat metadata is deliberately excluded from authority comparisons so a
  heartbeat does not invalidate already-issued tokens.
- A stale epoch fails at a bound ledger commit even if its process continues
  computing or dispatching messages.
- Epoch exhaustion and malformed or mismatched authority tokens fail closed.

## Implementation boundary

[`coordinator-authority.js`](../../src/core/lib/db/tables/coordinator-authority.js)
owns the typed authority record, immutable stable-request receipts, strict
readback, conditional state transitions, token validation, and portable ledger
fence construction.

[`execution-ledger.js`](../../src/core/lib/db/tables/execution-ledger.js)
accepts a stable coordinator-authority token and routes its transaction-bearing
mutation paths through one guarded writer. When a token is bound, that writer
adds the stable-tuple fence in the same table transaction and distinguishes a
stale authority from unrelated transaction failures. Existing unbound
construction remains available for non-coordinator local and test paths; it
does not claim current coordinator authority.

No production source currently creates this authority store or passes a token
to `createExecutionLedger`. The current operator and resident path is therefore
still unbound. Schedule-control mutations retain only their local owner fence,
and application-state mutations are outside this transaction domain. Several
admission and scheduling events also retain epoch `0`; the implemented epoch
stamp is complete for new physical attempt assignments, not yet for all
coordinator provenance history.

The authority record is deliberately co-located with ledger records rather than
placed only in the deployment control table, because the generic transaction
contract cannot atomically condition a ledger write on another table.

Existing invocation-attempt generations remain a separate, narrower fence.
Coordinator epoch authority composes with them: the current coordinator must
be authorized, and the attempt must still be the current generation for its
invocation.

Code paths that mutate a different physical destination do not gain a durable
fence merely by carrying an epoch value. A managed destination outside the
ledger transaction domain still needs a destination-local authority condition
or a future provider transaction primitive that can atomically span the
relevant records.

## Durable-store audit

The current database adapters establish different boundaries:

- DynamoDB supplies provider-backed strongly consistent reads and atomic
  conditional transactions, making it the current production candidate for
  exact epoch-authority transitions and fences.
- LMDB serializes local transactions and can exercise the same state machine on
  one durable volume. It cannot establish recovery after loss of that host or
  volume.
- The vanilla adapter is a deterministic test aid. It persists only on clean
  close and cannot substantiate multi-process or crash-safe authority.

None of the generic adapters exposes a store-authoritative clock or an atomic
predicate such as “replace only when the store says this lease has expired.”
The condition vocabulary supports exact equality, existence, absence, and
prefix matching, but not authoritative expiry. Adding an `expires_at` field
from a coordinator clock would therefore not close the automatic-recovery
contract.

tests.

## Honest boundary

- Confirmed takeover is storage-safe epoch replacement, not automatic failure
  detection.
- The production runtime does not yet acquire or require this authority.
- Schedule-control and application-state mutations are not coordinator-fenced.
- Admission and scheduling history does not yet consistently carry the bound
  epoch even when its transaction is fenced.
- A crashed active coordinator leaves availability blocked until an operator
  deliberately confirms a successor.
- Heartbeats can inform that decision but never authorize it.
- Epoch fencing prevents stale authoritative commits; it cannot stop physical
  execution or retroactively make unmanaged external effects exactly once.
- Automatic coordinator recovery, provider runtime permissions, reconstruction
  after replacement, and a two-node trusted recovery proof remain outside this
  slice.
