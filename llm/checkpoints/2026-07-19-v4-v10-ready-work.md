## Product direction retained from the project reset

The north star remains:

> Wharfie turns a normal TypeScript CLI with named activities into a
> self-contained executable that can run locally, remain resident as a durable
> worker, and coordinate work across a trusted set of machines—without
> requiring Node, containers, Kubernetes, or a hosted orchestration service.

The broader motivation is to let work expressed locally—especially work
authored with an LLM—outlive a chat or terminal session and become an
inspectable, evolvable durable service with very little operational ceremony.

The accepted scope choices are:

- nodes are trusted; a trustless or Byzantine mesh is out of scope;
- one coordinator is enough initially, provided its durable state permits
  robust recovery after coordinator loss;
- Wharfie is not general cloud IaC, but a packaged app may use the operator's
  credentials through finite Wharfie abstractions to create the nodes and
  resources it needs;
- Node/TypeScript is the authoring and runtime center. Native Node bindings,
  subprocess protocols, or WASM may serve measured hot paths without turning
  the public framework into a multi-language runtime;
- exactly-once language must stay narrow and evidence-backed. Logical
  singularity belongs in the state-machine/effect abstractions; arbitrary user
  code is never claimed to execute physically exactly once;
- CLI/operator JSON is the primary interface; a web UI is later and optional;
- v1 and backward compatibility are abandoned; breaking changes are preferred
  when they reach the cleaner eventual design faster; and
- portable SEA artifacts, not containers or a hosted control plane, remain the
  default distribution boundary.

## Strict workflow authoring contract

The schema remains `schemaVersion: 2` and now accepts an optional `workflows`
map. The compiler, generated embedded manifest, immutable revision contract,
and returned package contract preserve the validated definitions exactly.

Each workflow is revision-bound plain JSON with:

- one through 64 uniquely identified ordered steps;
- an aggregate exact-JSON UTF-8 ceiling of 1 MiB;
- exactly `activity`, `timer`, and `signal` step kinds;
- activity references restricted to activities declared by the same manifest;
- positive safe-integer timer delays;
- signal names equal to their stable step IDs; and
- one explicit activity input selector: whole workflow input, a JSON literal,
  or the persisted output of one named earlier step.

Array order is the entire continuation graph. The contract has no executable
decider, branch, loop, parallel step, child workflow, JSONPath evaluator,
template callback, retry policy, cron schedule, or early-signal inbox.

ADR 0019 defines the runtime contract that the next tranche must implement:
one immutable content-addressed plan, one active cursor, persisted step outputs,
atomic activity-terminal/continuation advance, timers decided once, current-wait
signals, run-level cancellation, and exact revision pinning.

## V10 ledger isolation

The ready-work mutation changes the transaction contract, so this tranche uses
fresh identities instead of reinterpreting retained records:

- execution-ledger schema: `10`;
- ledger sort-key namespace: `ledger/v10/`;
- default table: `wharfie-execution-ledger-v10`;
- manual-run identity domain: `wharfie:manual-ledger-run:v10`;
- effect-projection key domain: V10;
- paired run-history directory: schema/partition V8; and
- ready-work partition codec: V1, with ledger schema 10 included in its
  content-addressed partition identity.

V9 ledger and V7 directory records remain inert. There is no migration reader,
fallback, reinterpretation, or dual write. The managed-effect destination
identity deliberately remains version 8 because changing a control-ledger
storage schema does not change the independently durable destination operation.

## Transactional ready-work locator

Every ordinary manual lifecycle transition now derives at most one current
locator and creates, replaces, or removes it in the same transaction as the
event, transition receipt, run head, run/invocation/attempt projections, and
run-history directory.

Current dispatched kinds are:

- `ACTIVITY` for a `RUNNABLE` manual invocation; and
- `RECOVERY` for the one exact `CLAIMED` or `STARTED` attempt of a `RUNNING`
  manual invocation.

`TIMER` and framework-only `CONTINUATION` records are strict, tested codec
kinds reserved for the workflow state machine. Managed-effect successor runs
retain their dedicated lifecycle and intentionally produce no resident
ready-work row.

A row binds app, revision, run, run version, event sequence, eligibility time,
kind, invocation, generation, and—when applicable—attempt or continuation
coordinates. It is a replaceable locator, never execution authority. Its
portable ordering key is ascending persisted eligibility time followed by the
opaque run identity. Queries are bounded to 100 rows, use scope-bound canonical
opaque cursors, and never cross an app/revision partition.

The resident fully paginates the exact embedded/prepared revision. For every
candidate it rebuilds the authoritative event fold and checks the row's exact
run version, sequence, invocation, generation, attempt, status, and persisted
eligibility timestamp before entering an ordinary fenced transition. Fifty
stale rows cannot hide valid work on a later page. A malformed row is skipped
without dispatch while its raw key still advances pagination.

## Repair and restart behavior

`repairReadyWork` reconstructs one known manual run's expected locator from its
authoritative event fold. Its only compare-and-swap guard is the exact run head:
projection bytes may be corrupt and therefore are never trusted as transaction
conditions. Under one unchanged head, concurrent repairs converge by writing
the same canonical locator and deleting the same observed stale locator.

Idempotent manual submission replay repairs a known run best-effort. A head
race means a normal lifecycle transition won and atomically maintained its own
row, so that particular conflict does not turn a valid duplicate submission
into failure. The resident similarly repairs valid stale locators and ignores
only this winning-transition conflict.

The tests prove missing-row reconstruction, nested/object-valued corruption,
concurrent repair, repeated stale-row deletion, cross-revision cursor refusal,
corrupt-row page progress, full stale-page traversal, started cancellation,
uncertainty removal, managed-effect successor exclusion, and exact runnable and
recovery rows across two real LMDB close/reopen boundaries.

A completely missing locator whose run ID is unknown is not automatically
discoverable from the index itself. Normal process/coordinator failure cannot
create that state because the row and lifecycle commit atomically. Repair after
external storage corruption currently requires a known run ID (for example a
stable submission replay or internal maintenance caller). A future bounded
maintenance/operator reconciliation path may use the run directory; the idle
resident must not silently return to full-history scheduling scans.

## Known limits and ordered next work

1. Implement the minimal workflow plan/input/output payload schemas, workflow
   trigger, stable workflow/run/continuation identities, and rebuildable cursor
   projection in the V10 event fold.
2. Implement start and one compound activity-success transition that persists
   verified output, consumes the current continuation, materializes the exact
   next input, and atomically creates the successor row or terminal outcome.
3. Add timer schedule/fire and current-wait signal accept/reject transitions,
   all conditioning on the same run head/cursor. Then add run-level workflow
   cancellation so no continuation can race past retained cancellation intent.
4. Teach the resident to verify and consume V10 workflow `ACTIVITY`, `TIMER`,
   and exceptional framework `CONTINUATION` locators without weakening the
   existing manual/recovery authority checks.
5. Mount shared source and packaged workflow start, signal, inspect, cancel,
   and worker commands only after the core transitions are singular under
   replay and response loss.
6. Prove each workflow ambiguity boundary with process kill, LMDB reopen, and
   relocated SEA tests. Then add startup-on-boot installation and health before
   multi-host leases, provider-backed deployment, or coordinator failover.

Not implemented at this checkpoint: workflow runs/cursors/outputs, workflow
start or signal commands, timers, schedules, workflow cancellation, OS service
installation, multi-host placement/leasing, provider resource creation, generic
retries/compensation, or a web UI.
