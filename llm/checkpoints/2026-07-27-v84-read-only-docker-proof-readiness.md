## Restart summary

Wharfie's golden path remains a normal TypeScript/Node CLI that becomes one
approachable portable executable, runs locally or remains resident as a
durable service, and coordinates work across trusted machines without
requiring Node, containers, Kubernetes, or a hosted orchestration service on
the target machines.

The product exists to carry useful software beyond the coding session that
created it. It should preserve both executable behavior and legible durable
truth so a person or later coding session can follow, recover, and evolve the
work.

The settled project boundaries remain:

- nodes are trusted;
- one authoritative coordinator is acceptable initially when its durable
  authority is fenced and recoverable after coordinator loss;
- V1 and backward compatibility are abandoned;
- Wharfie is not general cloud IaC;
- finite Wharfie abstractions may use normal operator credentials to create
  only the resources they require;
- TypeScript/Node is the public authoring path, while measured Node-API, WASM,
  or other native hot paths remain possible behind versioned boundaries;
- exactly-once claims are made only where durable evidence and the managed
  destination's atomic effect semantics support them; and
- one executable and a machine-readable CLI remain the primary operator
  surface; a web UI is optional and later.

The standing working mode is local repository and Git CLI work rather than
PR/issue churn. Breaking changes are acceptable. Focused commits and pushes
are authorized. Use exact Node 24.13.1. Jest validation must disable coverage
and cache, run in disposable temp roots, and remove all generated bytes
immediately. Never run native LMDB, native SEA creation on this Mac, or
block-device tools locally. Live AWS, disposable hosts/EBS, formatting, and
other external mutation require explicit approval.

V83 committed the bounded Linux/amd64 Docker proof driver, verifier, strict
`whlp2` receipt, and private checksummed publication boundary. It has not been
run. V84 adds a standalone, mutation-incapable readiness observer so an

## Closed semantic boundary

The decision engine captures exactly eight semantic ports:

```text
readObservedAt
observeRepository
observeDockerEndpoint
observeDockerDaemon
observeDockerImage
observeDockerContainer
observeHostTemp
observeOutput
```

There is no port capable of creating, starting, stopping, removing, pulling,
building, publishing, reserving, or otherwise mutating a Docker object or
filesystem path.

Inputs, options, ports, tagged observations, and reports require exact own data
properties. Accessors, symbols, extra keys, malformed numeric encodings, and
oversized port results fail closed. The inspector snapshots repository and
image state twice. A report is serializable only when it is branded as an
actual result returned by the inspector; callers cannot fabricate a
ready-looking plain object and pass it to the serializer.

The schema is version 1 and fixes:

```json
{
  "safetyClass": "read-only-no-container-mutation",
  "authority": "none",
  "authoritative": false,
  "freshness": "point-in-time-only"
}
```

The public subject binds the source/tooling commit, immutable image ID,
deterministic container name, and a digest of the output root without exposing
that raw path. Public filesystem observations omit host device IDs; those IDs
are used only internally to decide whether capacity is shared.

The blocker/advisory decision covers:

- exact clean and stable repository HEAD;
- exact committed/live bytes for the V83 driver, verifier, proof protocol, and
  both V84 files;
- one bound local Unix Docker endpoint;
- observable Linux daemon architecture, memory, and CPU advisory;
- exact, stable, already-present Linux/amd64 image identity;
- absent, running, foreign, or exact stopped-owned container-name collision;
- canonical writable host temp and output paths;
- existing proof-commit output collision; and
- conservative capacity for host staging and output, including a combined
  162 MiB requirement when both observations are on one filesystem.

## Production read-only adapter

The adapter is standalone and does not import the mutating V83 driver. Its
filesystem imports are limited to `access`, `lstat`, `open`, `realpath`, and
`statfs`, plus read-only filesystem constants. Live tooling bytes are read
through `O_RDONLY`, `O_NOFOLLOW` where available, and stable
descriptor/path/device/inode metadata checks.

Only these positively enumerated child operations can compile:

```text
git status
git rev-parse
git ls-tree
git cat-file blob
docker context show
docker context inspect --format <endpoint-only-template>
docker info --format <narrow-template>
docker image inspect --format <narrow-template>
docker container ls --format <ID-only-template>
docker container inspect --format <identity-and-required-labels-template>
```

The Git reads disable optional locks, lazy fetch, fsmonitor, untracked-cache
updates, hooks, replacement objects, system/global configuration, paging, and
terminal prompts. Status includes all untracked files and disables rename
processing.

Docker endpoint resolution follows effective CLI precedence:
`DOCKER_CONTEXT`, then `DOCKER_HOST`, then `docker context show`. Remote,
TCP, SSH, malformed, and non-Unix endpoints block. The chosen endpoint is
resolved once and privately bound for the entire scan; every daemon/image/
container read receives it through an explicit `--host`. Broad inspect
objects, environment arrays, mounts, and arbitrary labels are never requested.

Every child has bounded output and a 30-second wall clock, runs without a
shell in a detached process group, and is force-killed and reaped on timeout,
overflow, SIGINT, or SIGTERM. Interruption is latched so later observations
cannot spawn another process.

Filesystem observation never creates a descendant. It walks to the nearest
existing output ancestor, rejects symlink/noncanonical anchors, uses only
access and `statfs`, and detects an already-present commit output. Both the raw
Node temp path and its resolved target must be canonical absolute non-root
paths. The final audit specifically found and closed the case where a
non-root temp alias resolved to filesystem root.

## Honest boundaries

V84 is admission observation, not environment evidence:

- the readiness command itself has not been run against the user's real Docker
  endpoint or an actual image;
- the V83 driver has not run and no `whlp2` receipt exists;
- no Docker daemon, image, container, registry, network, native build, native
  SEA build, LMDB, block device, or AWS API was touched during V84;
- a Unix socket proves local transport syntax, not daemon identity; the socket
  can proxy, move, or be replaced;
- Docker context/socket access, PATH-selected Git/Docker executable bytes, and
  local repository/Docker configuration remain trusted caller-controlled
  inputs;
- stopped-container labels are forgeable cleanup eligibility, not
  authenticated ownership;
- access and `statfs` do not cover inode, quota, thin-provisioning, Docker
  backing-store, or future build-layer exhaustion;
- image presence and rootfs identity do not prove provenance, signatures,
  bootstrap behavior, emulation success, dependency availability, build
  success, or proof execution;
- repository, image, container, path, and capacity observations can change
  immediately after inspection;
- the later V83 driver repeats its own exact clean-HEAD, image, collision,
  cleanup, and publication checks;
- the later proof still uses unrestricted bridge networking;
- reports and eventual proof receipts are unsigned; and
- no systemd residency, reboot recovery, provider-backed coordinator
  replacement, trusted multi-node placement, or exactly-once destination
  semantics are added here.
